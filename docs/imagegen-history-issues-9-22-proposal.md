# e图宝历史任务优化方案：Issue #9 与 #22

日期：2026-10-05

状态：已按确认方案完成实现与本地自动验证；真实模型和安装包验收需单独核对

后续展示调整（2026-10-05）：用户明确要求普通生图查看全部图片，因此普通页改为「全部生图」汇总，不再按来源隐藏结果。下文普通页“来源隔离展示”的原方案由这条要求替代；电商任务恢复、画布管理及按来源删除和清空保护继续保留。

分析依据：两个 issue 的正文、改造前源码 `7fa64f3189`。第 2 节保留改造前问题分析，第 10 节记录本次实施结果。

## 1. 我对这两个问题的理解

这两个 issue 是同一个需求的两个层面：**各模式管理自己的历史，电商模式能重新打开一整套商品图任务。**

| 问题 | 核心诉求 | 对应改造 |
| --- | --- | --- |
| [#9：历史记录来源混杂、清空范围不一致](https://github.com/cqai-club/ebao-studio/issues/9) | 普通生图、电商套图、无限画布的记录各自独立；清空不能误删其他来源 | 统一来源识别、独立筛选状态、按来源删除与清空 |
| [#22：电商历史入口与整套恢复](https://github.com/cqai-club/ebao-studio/issues/22) | 电商结果区点击展开任务列表；既能看完成任务，也能看进行中任务；点击恢复配置和整套结果 | 电商任务列表、完整配置快照、任务状态与整套结果恢复 |

我理解的目标操作是：

> 进入电商模式 → 点击「新建商品」旁边的「历史任务」 → 选择一个商品套图任务 → 左侧恢复该任务配置，右侧显示整套结果或当前进度 → 进行中的任务继续更新。

入口位置以用户最新确认为准：放在电商结果区标题的操作栏，与「新建商品」相邻。

“恢复”是重新打开已有任务。只有用户明确点击生成、重试或重新生成，才提交新的生成请求。

电商历史的一条记录对应**一次完整套图任务**。同一个商品执行两次整套生成，应有两条可辨认的记录；一条记录包含主图、卖点图、细节图等槽位及其状态。

## 2. 当前代码确认了什么

以下为源码核对结论，没有启动桌面应用现场复现，也没有确认用户机器的安装版本。Issue 中的行号与当前源码已有偏移，下面使用当前版本的位置。

| 已确认现状 | 影响 | 源码证据 |
| --- | --- | --- |
| 电商模式仍显示左侧历史栏，占用约 220–300px | 页面实际形成“历史栏 + 配置 + 结果”三列，结果空间受挤压；不符合将入口放到「新建商品」旁边的要求 | [界面挂载][ui-shell]、[栏宽样式][ui-css] |
| 电商历史对全部 `history` 分组，仅过滤关键字、模型、比例，没有先过滤来源 | 普通生图、画布记录会进入电商历史；筛选选项也取自全部记录 | [历史筛选][ui-filter] |
| 普通瀑布流已排除带画布、电商、项目或槽位标记的记录 | 普通方向已有隔离能力，但不能保证电商方向也隔离 | [普通来源判定][normal-origin] |
| 电商历史「清空」调用全局 `historyClear`，Host 删除全部历史条目及图片文件 | 会实际删除其他模式的生成历史和对应图片，不只是隐藏列表 | [客户端清空][ui-clear]、[存储清空][store-clear] |
| 普通与电商复用 `historyQuery`、模型和比例筛选状态 | 从一个模式切换到另一个模式时，旧筛选会影响新列表 | [共享筛选状态][ui-filter-state]、[筛选消费][ui-filter] |
| `viewEcommerceProject` 恢复的是分组结果，没有恢复商品表单、参考图和完整生成配置 | 左侧可能还是上一个商品，右侧已经换成历史商品；导出也可能混用当前表单信息 | [结果恢复与导出][ui-restore] |
| 电商参考图是页面会话状态；历史恢复代码把旧图生图请求降为文生图 | 旧记录无法忠实恢复参考图及原生成方式，不能靠修改按钮文案解决 | [参考图边界][ui-restore] |
| 历史条目在成功生成后才写入，队列运行态保存在 Host 内存 | 只读历史文件无法列出还没有任何结果的套图，也无法可靠表达失败、等待和取消状态 | [完成后写历史][runtime-save]、[内存队列][task-queue] |
| 主图生成完成后，由页面 effect 提交其余套图请求；新建商品或开始另一套生成会清除旧接力状态 | 旧主图可能仍在生成，但尚未提交的后续图片可能不再生成；页面卸载也会丢失接力状态 | [页面接力][ui-anchor]、[生成与新建][ui-submit] |
| 整套生成使用草稿中的 `projectId` 或新 ID，单槽位重生成复用原请求 | 若草稿已有 ID，多次整套生成可能混成同一条历史；同槽位多个尝试也可能重复计入进度 | [生成与新建][ui-submit]、[结果合并][ui-result-merge] |
| 历史保留上限是全局 50 条生成记录，超过后按条目截断并删文件 | 普通生图可能挤出电商图；一套商品图可能只剩一部分，配置快照也无法补回已删除图片 | [保留上限][history-limit]、[逐条淘汰][store-retention] |

因此，方案需要同时补齐**来源隔离、完整任务存储、运行状态和界面恢复**。仅增加一个下拉列表，仍会留下配置缺失、进行中任务不可见、套图被截断的问题。

## 3. 推荐方案

1. 普通生图、电商套图、无限画布分别维护自己的生成历史列表、搜索条件和删除范围。
2. 电商模式取消常驻左侧历史栏，在结果区「新建商品」旁边放置紧凑的「历史任务」按钮，顺序为 `[历史任务 ▾] [新建商品]`，点击后在历史按钮下方展开列表。
3. 保留“左侧商品配置、右侧套图结果”的主体布局。历史列表展开时浮在页面上方，不推挤工作区。
4. 电商任务在开始生成时就保存，包含完整配置、参考素材、计划槽位、运行状态和结果；不必等第一张图片成功才出现在列表中。
5. 选择任务时同时恢复左侧配置和右侧结果，并持续获取该任务的状态。页面当前选择与后台任务执行分开管理。
6. 将电商主图接力放到 Host 管理，使新建商品、查看其他任务或关闭面板不影响已有套图的编排。
7. 以完整套图任务为保存和清理单位，避免共享的单图保留上限截断项目。

## 5. 交互与数据规则

### 5.1 三个来源各管自己的生成历史

| 模式 | 展示单位 | 搜索/筛选 | 删除/清空范围 |
| --- | --- | --- | --- |
| 普通生图 | 普通生成记录，保持现有瀑布流 | 独立关键字、模型、比例 | 仅普通来源生成记录 |
| 电商套图 | 一次完整套图任务 | 独立商品名/任务名/提示词、状态、模型、比例 | 仅电商任务及其自有数据 |
| 无限画布 | 画布来源生成记录，可按画布项目聚合 | 独立关键字、模型、比例、画布项目 | 仅画布来源生成记录；不等同于删除画布文档 |

画布生成历史与现有“画布项目列表”、画布撤销历史、素材导入选择器是不同功能。来源隔离针对生成历史；画布主动导入其他模式图片的能力继续保留，图库收藏也独立管理。

### 5.2 打开任务的流程

1. 切换前保存当前商品草稿；按草稿/任务分别存储，避免多个商品共用一个表单状态。
2. 读取所选任务的配置快照、素材和槽位状态，界面显示加载反馈。
3. 读取成功后，一次性应用配置和结果、切换当前任务并收起历史列表。失败时保留原工作区，显示重试。
4. 订阅或轮询当前任务的状态；其他电商任务仍由 Host 执行，其摘要也能在历史列表中更新。
5. 快速点击 A、B 时以最后一次选择为准；过时的图片加载、AI 帮写或素材上传结果不能写入新选中的任务。

查看 B 时，后台 A 完成只更新 A 的任务记录和列表摘要，不替换 B 的配置、结果或错误，也不切换工作区。同槽位多次尝试保留记录，默认显示当前尝试及可用结果；总进度按计划槽位计算，不把重试累计为额外计划图片。

打开列表、选择任务、读取结果、恢复表单这四类操作均不调用生成提交。恢复后的导出也从所选任务快照取值，不能混用另外一个草稿。原模型或渠道当前不可用时明确提示，不静默替换成当前默认模型。

### 5.3 状态定义

| 状态 | 用户看到的含义 |
| --- | --- |
| 排队中 | 计划已保存，尚未开始产生结果 |
| 生成中 | 还有槽位在执行、排队或等待主图依赖 |
| 已完成 | 计划槽位全部成功完成 |
| 部分失败 | 任务已结束，有可用结果，也有失败槽位 |
| 失败 | 任务已结束，没有可用结果，且存在失败 |
| 已取消 | 用户明确取消；已生成结果可以保留查看 |
| 已中断 | Host 重启等情况下无法继续确认原执行状态；保留已完成结果，提供明确恢复选项 |

状态由完整槽位计划和执行状态计算。不能把“历史里已经有两条成功记录”直接显示为“已完成 2/2”，因为原任务可能计划生成六张。

### 5.4 删除与清空

建议把电商列表的批量入口明确命名为**「清空电商已结束任务…」**，排队中、生成中任务继续保留。要停止正在执行的任务，使用独立的明确取消操作；删除不隐式取消生成。

确认文案示例：

> 将删除 8 个已结束的电商套图任务及其自有结果。1 个进行中任务会保留。普通生图记录、画布记录与文档、图库收藏不受影响。

- `已结束` 包括完成、失败、取消及已中断任务；保留进行中的任务。
- 单项删除也仅适用于已结束任务。排队中、生成中任务的菜单提供明确的取消操作，不提供删除；确认运行结束后才允许删除。
- 搜索和筛选不暗中改变清空作用域；弹窗列出的是完整电商来源中将删除的终态任务数量。
- Host 验证来源和状态，并在执行时重新校验；不能只靠前端先过滤几个 ID 来保证范围。
- 删除失败要恢复/重新读取实际列表并说明错误，避免当前“本地看似删除、服务端还在”的状态。
- 删除自有图片前检查共享引用，不能让保留的图库、画布或其他任务出现失效图片。

当前图库收藏、画布导入已有独立资产复制机制，这部分可以继续复用；新增电商任务资产不要反向依赖随历史清理消失的 URL。普通/画布历史也使用明确的来源名称和数量。清空画布生成历史不隐式清空画布文档。

## 6. 实施设计

### 6.1 统一来源判定与作用域

抽取 Host、客户端共用的来源判定，而不是各处各写一个过滤条件：

- 有明确 `canvas` 元数据：画布来源。
- 有电商 `workflow`，或历史电商项目/槽位标记：电商来源。
- 无上述来源标记的旧记录：普通生图，兼容没有 `workflow` 的 legacy 数据。
- 同时存在冲突标记或不足以确认归属的数据：保留并记录异常，不自动加入任何来源的批量删除。

各来源拥有独立筛选状态，分组前先确认来源。Host 提供按来源列举、删除和清空的接口，单项删除也校验归属；批量修改沿用当前串行化写入能力。

### 6.2 电商任务作为持久化的一等记录

新增电商任务存储，建议记录：

```text
电商套图任务
├── 任务 ID、商品/任务名称、创建时间、更新时间、版本
├── 原始配置快照
│   ├── 商品名、商品说明、平台、语言（含自定义值）、类目
│   ├── Provider / Channel、实际使用模型、比例、清晰度、detail
│   ├── 全部套图槽位、描述、启用状态、张数、参考图角色
│   └── 逐图提示词及用户覆盖内容
├── 原始商品参考图、风格参考图的持久化资产引用
├── 完整计划槽位
│   └── 槽位编号、主图依赖、每次生成尝试、状态、结果引用、错误
└── 整体状态与迁移完整度标记
```

原始配置快照固定保存；运行状态和结果另行更新。任务列表只返回摘要与缩略图引用，打开任务时才读取详情，避免每次刷新传输全部图片。

明确区分草稿身份和生成任务身份。当前 `projectId` 接近批次标识，但可能复用草稿内的 ID；新实现可将其严格定义为任务 ID，或增加 `runId`，并兼容旧字段。无论字段名如何，每次整套确认生成必须分配新任务 ID；槽位重生成仍归于原任务，但增加尝试记录。初版无需再引入多层商品项目管理。

参考图和结果保存到 Host 的任务资产目录，不把 base64 塞进列表响应，也不只保存在浏览器草稿中。凭据继续由现有 Provider 管理，任务快照不保存 API Key。

### 6.3 电商编排由 Host 执行

复用现有图片生成队列，新增电商套图编排层，提交完整计划：

1. 保存完整计划和素材，然后创建主图子任务。
2. Host 观察主图完成，根据已保存的依赖安排后续槽位。
3. 整套提交使用稳定的请求去重标识，网络重试不创建第二套任务；槽位派发按“任务 + 槽位 + 尝试”校验，防止多个观察者重复提交；明确重生成才增加尝试次数。
4. 主图失败时，依赖槽位显示失败原因/等待重试，不无限显示生成中。
5. 主图锚定后的真实请求另行记录，保留实际生成依据，不能覆盖原始商品参考配置。

查看任务只读任务详情、状态和结果，不重建页面中的自动提交 effect。无需为此重写普通生图或画布的通用队列。

**重启边界：**当前内存队列不提供跨 Host 重启续跑能力。本次应保证保存配置与已完成结果，并将无法确认的执行标记为中断。不能承诺重启后自动续跑；只有能够查询原服务任务或可靠去重时才恢复，否则由用户明确重试，避免重复请求和费用。

### 6.4 整套任务保留策略

电商新任务的结果应由任务存储拥有，或被明确的持久引用保护。不能继续只引用随共享 50 条历史上限被删除的图片。

本次实施采用以下策略：普通生图和画布生成历史分别保留最近 50 条；共享旧索引中的电商记录按完整项目保留最近 50 个项目。新电商任务及其自有参考图、结果独立保存，不随共享索引淘汰，目前不设置自动数量淘汰，由用户删除单套任务或清空已结束任务。进行中任务不可删除或被清空；停止执行使用明确的取消操作。

新电商任务提交上限为 100 个计划槽位、40 张参考素材，单张图片最多 24 MiB，请求体最多 64 MiB。自有资产会随整套任务删除；本次没有引入磁盘总容量自动回收策略。

### 6.5 旧记录兼容

- 无来源标记的 legacy 普通记录继续归普通生图，不因新增电商存储而丢失。
- 现有电商图片按 `projectId` 聚合，迁入“旧版任务”视图；没有项目 ID 的电商记录仍保留为可查看结果的旧记录。
- 从已有记录能确定的商品名、模型、比例、提示词和结果可保留；不能凭生成后的提示词可靠反推全部商品配置、参考图和原计划张数。
- 缺失字段明确标记「旧版记录，配置不完整」，不拿当前草稿或默认配置冒充原配置；展示“现存 4 张”，不虚构 `4/4 已完成`。
- 旧记录缺原始配置与参考图时只展示可用结果和明确提示，不提供完整配置复制或直接重试入口。
- 新建任务满足完整恢复要求；旧记录允许有限恢复，这是历史数据没有保存对应内容造成的限制。
- 迁移前备份现有元数据，迁移过程可重复执行，校验成功后再切换读取，不删除原数据作为迁移步骤。

## 8. 验收方案

| 验收场景 | 预期结果 |
| --- | --- |
| 同时存在普通、画布、电商记录，分别打开各生成历史 | 三个来源互不混入；普通 legacy 仍可见；各来源筛选状态互不影响 |
| 电商任务还没有任何结果 | 已作为一条任务显示，状态为排队中/生成中，总数来自完整计划 |
| 同商品生成两套，某一槽位又重生成一次 | 两套任务独立；槽位重生成保留在对应任务内，有尝试记录，不产生重复套图列表项 |
| 打开完成任务 | 商品资料、原始参考图、平台/语言/类目、Provider/模型、比例/清晰度、槽位结构、逐图提示词及结果一致恢复；导出来自该任务 |
| 打开进行中任务 | 已有结果可见；完成数量、等待依赖和后续状态持续更新，不重复计数 |
| A 在等待主图时打开 B、另建商品、关闭再打开面板 | A 的 Host 编排继续；打开任务动作不新增生成提交 |
| 双客户端查看同一任务、提交响应丢失后重试同一请求 | 同一完整计划只创建一个任务，各计划槽位不重复派发 |
| 快速选择 A 后选择 B，A 的图片更晚加载完成 | 最终仍展示 B 的配置和结果；旧 AI/上传回调不污染 B |
| 查看 B 时，A 或普通生图/画布任务在后台完成 | 只更新对应任务及列表，B 的配置、结果和错误保持不受影响，不切换工作区 |
| 读取失败、删除失败、状态连接断开 | 显示失败和恢复入口；不显示虚假成功；连接断开显示最后已知状态和更新时间 |
| 电商清空时有普通/画布/图库数据和进行中电商任务 | 只删除确认范围内的电商终态任务；其他来源及进行中任务保留；共享素材引用仍有效 |
| 累积超过原来的 50 条生成记录，混合不同来源 | 被保留的电商任务整套完整，不因普通记录增加而被截断 |
| 恢复旧版电商记录 | 现存结果可查看，缺失配置有明确标记，不伪造张数，不静默改变生成方式 |
| Host 重启后重新打开 | 已保存配置/结果仍在；未能确认的原执行显示中断，不自动重新收费生成 |
| 工作区宽度约 1440、1280、1024、768、390px；矮窗口、深浅主题 | 入口可见；弹层不越界或裁切；列表内部可滚动；配置/结果可操作；键盘导航可用 |

测试重点放在真实行为：Host 来源清空保护、任务快照往返、未产生结果任务可见、异步选择竞态、主图接力与提交次数、整套保留和旧数据兼容。

补充 `scripts/smoke.mjs` 的反向断言：**电商历史不含普通或画布任务**，同时保留普通瀑布流排除电商的已有断言。实施后运行插件测试/类型检查和相应仓库门禁，再做实际 Beta/Stable 桌面验证；仅通过源码测试不能替代历史恢复的桌面验收。

## 9. 分析结论与边界

我建议把 #9、#22 作为一次完整功能改造推进：**模式内历史隔离，电商整套任务持久化，从「新建商品」旁的历史列表进入任务，配置与结果一起恢复。**

新任务可以实现完整恢复；旧任务缺少原始参考图和配置的部分无法凭空补回，必须在界面如实说明。Host 跨重启自动续跑是另一个能力，本方案先保证不丢配置和结果、不在恢复时重复生成。

历史隔离改造阶段仅涉及图像插件和本文档，未更新 issue 或发布安装包；下列记录保留该阶段的范围和验证结果。图像插件、短视频及多平台发布的后续改动统一通过仓库检查后交付到开发分支。
